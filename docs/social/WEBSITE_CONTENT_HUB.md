# Website + content hub architecture

**Framework:** unchanged — React 19 + Vite + TypeScript + react-router-dom 7 + Tailwind 4.
No framework change, no new routing convention, no new build step beyond one optional generator.

## Routes

| Route | Component | Purpose |
|---|---|---|
| `/` | `MediaHomePage` (via `HomeEntryPage`) | Public career-skills homepage for signed-out visitors |
| `/content` | `ContentHubPage` | Every lesson, filterable by pillar |
| `/content/:slug` | `ContentDetailPage` | One lesson: full readable text, sources, platform links, sharing |
| `/topics/:pillarSlug` | `TopicPillarPage` | One of the six pillars — `cv`, `interview`, `ai-task`, `money`, `applications`, `mindset` |
| `/social` | `SocialDirectoryPage` | The official account directory |
| `/about` | `HowJifunzeWorksPage` | Who it serves, the pillars, how content is chosen, what automation does and does not do |
| `/privacy`, `/terms` | existing pages | Unchanged |
| `*` | `NotFoundPage` | Unknown routes; unknown lesson and topic slugs render it too, with `robots: noindex` |

All six new public routes render inside `MediaSiteShell` — its own header and footer, deliberately
separate from the learning platform's shells.

### Signed-in routing is unchanged

`HomeEntryPage` still sends an authenticated admin to `/admin/dashboard` and an authenticated
learner to their default path. The only change is the signed-out branch: it used to
`Navigate to="/learn"`, it now renders the public homepage. `/learn` itself is untouched.

### Retired product routes

`/generate`, `/ideas`, `/studio`, `/trends`, `/insights`, `/platform`, `/training`,
`/team/members` and `/team/assignments` were removed in May 2026 and had been answering 404 ever
since. They now redirect to `/`. `/generate` matters most: Jifunze.ai's own April 2026 launch posts
on TikTok, LinkedIn and X still link to it, so anyone arriving from one now lands on what the brand
actually is instead of a dead end — and not on the frozen course catalog either.

## The canonical content ledger

`src/social/contentLedger.ts` defines `ContentItem`, one record per piece of content wherever it
ends up. **The ledger is the source of truth; platform APIs only enrich it.** Nothing here is ever
created by scraping a platform.

Fields: internal id · slug · title · summary · full body text · pillar · source type · original
source URL · sources with attribution · brief version · script version · video asset reference ·
thumbnail · caption · hashtags · publication status · approval status · published timestamp ·
per-platform publication records (post id, post URL, status, last metrics sync, metrics, error
summary) · content safety status · correction note · SEO fields.

The Postgres shape is `content_items` + `content_sources` + `content_publications` in
`supabase/migrations/20260820120000_social_ops_core.sql`.

### What the public site renders

Only records that are **both** `approval_status: 'approved'` **and** `publication_status:
'published'`. Enforced twice: in `isPubliclyVisible()` in the client, and by the RLS policy
`content_items_public_read`, so a mistake in one does not leak through the other.

### Why the site does not depend on embeds

Every lesson is published here as readable text, not only as an embedded platform post. A lesson
survives a deleted post, a rate-limited embed, a slow third-party script and a platform outage. The
detail page renders a video player only when a video asset actually exists; the steps are always
there. A test asserts a lesson with zero platform publications still renders fully.

### Where the lessons come from

`src/social/guides.ts` is **generated** from `orchestrator/contentBank.ts` — the same approved,
hand-written lessons the content engine draws from — by `npm run guides:generate`. Ids are
identical and `scripts/test-social-ops.ts` fails if they drift. Editing the guides by hand is
therefore a mistake; edit the content bank and regenerate.

No content was invented. No audience number, partnership, accreditation, course, certificate,
instructor, employment outcome or income outcome is claimed anywhere on the site.

## SEO and discovery

| Item | Where |
|---|---|
| Title, meta description, canonical | `index.html` (static default) + `usePageMeta()` per route |
| Open Graph + X card | both |
| Organization structured data | `index.html`, with `sameAs` listing all nine official accounts |
| WebSite structured data | homepage, via `usePageMeta` |
| Article structured data | each lesson detail page |
| `sitemap.xml`, `robots.txt`, `feed.xml` | generated by `npm run seo:generate` from the same modules the app renders from |
| Pinterest verification | `p:domain_verify` meta tag in `index.html` |
| Favicons, share image | `public/favicon.svg`, `public/og-image.png` |

### Known limitation — read this before promising rich link previews

This is a client-rendered SPA. `usePageMeta()` applies per-route tags **after hydration**. Search
engines that execute JavaScript read them correctly. **Social-network link scrapers generally do
not**, and will fall back to the static block in `index.html` — so every shared lesson URL currently
previews with the site-level title and image rather than the lesson's own.

That is acceptable for launch and unacceptable long term. The fix is to prerender the public routes
at build time (a `vite-plugin-ssg`-style step, or Vercel prerendering for the `/content/*` and
`/topics/*` paths) so the correct tags are in the served HTML. Tracked as a follow-up; not done
here because it changes the build pipeline, which was out of scope.

## Typography and colour

Plus Jakarta Sans is **self-hosted** from `brand/fonts` as woff2 in `public/fonts`, declared with
`@font-face` and scoped to `.jf-media`. No Google Fonts request: no third-party dependency on first
paint, no visitor IP handed to a font CDN, and the brand typeface renders offline. The frozen
learning platform keeps its own type entirely.

Colours are the approved set — violet `#7C3AED`, near-black `#0B0B12`, white — applied via scoped
utilities so nothing in the shared stylesheet changes for the frozen pages.

## Accessibility

Skip link · one `<h1>` per page with no skipped levels (asserted in e2e) · every social link has an
accessible name naming the platform, the handle and that it opens in a new tab · visible focus
rings on every interactive element · `aria-pressed` on the filter buttons with an `aria-live`
result region · 44px minimum touch targets · no horizontal overflow at 375px (asserted in e2e) ·
lesson video is optional and the full text is always present.

## Addendum (2026-08-21): the public latest-post feed

The landing page now includes a "Latest posts" section rendered from the cached publication
store via `src/services/publicFeed/publicFeedData.ts`. Contract:

1. Server-side sync (metrics workflow) normalizes permitted post metadata into
   `content_publications`; the browser NEVER calls a platform API and never sees a token.
2. RLS exposes only display-safe rows; the module maps them to display-safe fields (platform,
   permalink, type, pillar, caption excerpt, thumbnail/poster, published time, permitted public
   metrics, featured, last-synced time) — nothing else reaches the DOM.
3. UI states are exhaustive and honest: loading · live · stale (last sync older than 48 h,
   labeled) · empty (nothing published yet) · unavailable (store unreachable / migration not
   applied) · not configured (build without Supabase). Missing thumbnails fall back to a brand
   tile. Live credentials are NOT required to deploy the landing page.
4. No fixture ever renders in production; development fixtures exist only in tests.
